# CortexHeal Launch Readiness

## Completed Milestones (Live Demo Launch)
- **Database Connection Storm Fixed (DONE):** The massive 11-second DB ingestion blocking issue during scale tests was eliminated by removing a global Python lock and pre-warming a strictly bounded \minconn=10\ connection pool.
- **Safety-Gate-at-Scale Re-verification (DONE):** Successfully intercepted and paused 55/55 simulated concurrent bad agent runs in load testing. End-to-end detect-to-pause pipeline latency measured reliably at p50 ~10ms, p95 ~150-200ms.
- **Tenant Data Leak Fixed (DONE):** Cross-org isolation flaws in \pi_get_incidents\ and \pi_get_runs\ have been patched. Both endpoints (along with fleet and patterns) are now explicitly backed by permanent negative cross-org isolation tests in the CI suite.
- **Live Demo Runner & Embed (DONE):** The \cron_demo_runner.py\ script is fully configured to cycle through varied scenarios (Stuck Loop, Budget Overrun, Fleet) inside a restricted \demo_public\ org, automatically pruning old data. The frontend (\AuthGate.tsx\) successfully embeds this live queue as a read-only split-screen experience using a \VIEWER\ token.

## Known Open Items (Post-Launch Risk)
- **Missing Org-Isolation Test Coverage:** There remains a critical testing backlog for the rest of the control plane. The following 8+ org-scoped endpoints have ZERO permanent negative cross-org isolation tests, posing a silent regression risk:
  1. \GET /api/incidents/{incident_id}\
  2. \GET /api/incidents/{incident_id}/plan\
  3. \POST /api/incidents/{incident_id}/plan/approve\
  4. \POST /api/incidents/{incident_id}/plan/reject\
  5. \GET /api/runs/{run_id}\
  6. \GET /api/webhooks\
  7. \POST /api/webhooks\
  8. \DELETE /api/webhooks/{config_id}\
  9. \GET /api/notifications\
  10. \GET /api/audit/export\
- **SSE Fanout Architecture:** Server-Sent Events (SSE) fanout is implemented purely in-process. This works fine for a single backend replica, but will silently drop live updates if the backend is horizontally scaled to multiple replicas without a Redis pub/sub broker.
- **Webhook Dispatch Blocking:** Webhook dispatch remains synchronous, blocking the main telemetry worker thread. This poses a latency risk during incident bursts when reliable alerting is most critical.

- **SaaS Identity & Multi-tenant Provisioning (New Pivot):** The application has pivoted from a shared 'Public Demo' iframe to a Self-Service SaaS model. Users should arrive from the marketing site, hit an Auth gate, and enter their own isolated 24/7 tenant. Currently, CortexHeal uses manual API keys generated by existing admins. To support this SaaS flow, we must implement an Identity Provider (IdP) integration (e.g., Auth0, Supabase) and an automated signup/provisioning endpoint that creates a fresh \org_id\ and provisions an initial tenant key for new users.
